# Норма

Мобильное веб-приложение для дневника питания, персональных нутриентных норм и планирования задач. Исходный Java-проект Telegram-бота не изменяется.

Это адаптивный сайт для телефона, а не нативный APK/IPA. На смартфоне его можно открыть в браузере и добавить ярлык на главный экран. Камера для сканирования работает на `localhost` или по HTTPS.

## Что реализовано

- вход по российскому номеру с маской `+7 917 513-33-15`;
- автоматическая проверка четырёхзначного кода без кнопки «Войти»;
- локальный демо-режим и серверная авторизация через SMS-адаптер;
- дневник питания по датам и приёмам пищи, изменение массы существующей записи без создания дубликата;
- русский поиск с учётом опечаток, фильтр по категориям и постраничный каталог;
- избранное, КБЖУ и три наиболее значимых витамина/минерала в карточке;
- страница «О продукте» с описанием, КБЖУ и всеми доступными нутриентами на 100 г, процентами ДН и горизонтальными шкалами;
- поддержка профиля из **92 показателей**: основные нутриенты, витамины, минералы, 18 аминокислот, жирные кислоты и прочие вещества;
- показ только заполненных у источника показателей с сортировкой по вкладу в дневную норму;
- профиль пользователя: год рождения, пол, вес, рост, активность и цель;
- расчёт калорий по Миффлину–Сан Жеору, белка по массе тела и цели, жиров и углеводов;
- скруглённое калорийное кольцо с дугами по часовой стрелке и три плотно расположенных кольца белков, углеводов и жиров вокруг каждой из семи дат;
- единая скёркл-геометрия (`corner-shape: squircle`) для карточек, кнопок, окон и полей с обычным скруглением в старых браузерах;
- до двух избранных нутриентов на главной с фактом, нормой, процентом и кратким назначением;
- рекомендации по остатку нормы и помощник, учитывающий дневник и тренировки;
- Markdown в ответах помощника: жирный текст, заголовки, списки, ссылки и сохранение одиночных переносов строк без выполнения сырого HTML;
- распознавание всех отдельных продуктов, блюд и напитков на одном фото через серверный Moonshot API с моделью `kimi-k3`, текстовый помощник на `kimi-k2.6`;
- отдельная редактируемая масса и кнопка добавления у каждой распознанной позиции; добавленный продукт исчезает из списка, а «Добавить все» переносит оставшиеся в дневник;
- автоматическое уменьшение фото до 1280 px по длинной стороне и JPEG-сжатие перед отправкой; при сбое API показывается настоящая ошибка с повтором, без подменных AI-ответов;
- встроенная в карточку баланса панель из трёх равных рядов: галерея раскрывается слева от камеры без изменения высоты карточки; первые пять запусков камеры показывают совет и требуют подтверждения;
- сканер EAN-13, EAN-8 и UPC, ручной ввод штрихкода;
- серверный каталог PostgreSQL, импорт USDA FoodData Central и кэш Open Food Facts;
- задачи с описанием, своими разделами, датой или без неё, временем или без него, началом и концом, повторением, фильтрами и сортировкой;
- синхронизация профиля, дневника, задач, избранных продуктов и нутриентов, сообщений между устройствами при работающем API; ссылки избранного на удалённые продукты автоматически удаляются;
- cookie-сессии, которые не требуют вводить телефон при каждом открытии.

## Технологии

React 19, TypeScript, Vite, Express, PostgreSQL 17, `pg_trgm`, ZXing, Docker Compose и Caddy. Секреты внешних API используются только на сервере.

## Быстрый запуск без сервера

Нужен Node.js 24 LTS или новее.

```bash
# Выполняйте команды из корня проекта, например C:\Users\solov\IdeaProjects\Other\norma
npm install
npm run dev -- --host 0.0.0.0 --port 7100
```

Откройте `http://localhost:7100`. Введите любой корректный российский номер и демо-код **2410**.

В этом режиме:

- SMS не отправляется;
- данные сохраняются в `localStorage` текущего браузера;
- поиск работает по встроенному русскому демо-каталогу;
- фото и помощник требуют запущенного API с серверным ключом; при его отсутствии показывается ошибка, а не вымышленный результат;
- сканирование камерой доступно, но для получения продукта по штрихкоду нужен API;
- синхронизации между устройствами нет.

Для просмотра с телефона в одной Wi-Fi-сети откройте `http://IP-КОМПЬЮТЕРА:7100` и разрешите Node.js в локальном брандмауэре. Не используйте этот режим как публичный сервер.

## Полный локальный запуск

### 1. Настройки

Создайте `.env` из примера:

```bash
# macOS / Linux / Git Bash
cp .env.example .env
```

```powershell
# Windows PowerShell
Copy-Item .env.example .env
```

Для первого локального запуска значения можно оставить как в примере. Перед публикацией обязательно замените `POSTGRES_PASSWORD`, `SESSION_SECRET` и пароль внутри `DATABASE_URL`. Пароль в `DATABASE_URL` должен совпадать с `POSTGRES_PASSWORD`.

Случайный секрет можно создать так:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

Файл `.env` нельзя коммитить или отправлять другим людям.

### 2. PostgreSQL и API

С Docker:

```bash
docker compose up -d db
npm install
npm run server:dev
```

Во втором терминале:

```bash
npm run dev -- --host 0.0.0.0 --port 7100
```

Vite перенаправляет `/api` на `127.0.0.1:3001`. Проверка API: `http://localhost:3001/api/health`.

Без Docker установите PostgreSQL 17, создайте базу `norma`, пользователя `norma`, обновите `DATABASE_URL` и выполните `npm run server:dev`. Таблицы, расширение `pg_trgm` и индексы создаются при старте из `server/schema.sql`. Встроенные демо-продукты регистрируются только в полностью пустой базе; перезапуск сервера не восстанавливает записи, удалённые при очистке каталога.

### 3. Полностью в Docker

```bash
docker compose up -d --build
```

Приложение будет слушать `http://127.0.0.1:3001`. PostgreSQL и приложение не открываются напрямую в интернет. Остановка:

```bash
docker compose down
```

Данные PostgreSQL сохраняются в Docker volume `postgres-data`. Команда `docker compose down -v` удалит их.

## USDA FoodData Central

### Почему локальная копия, а не запросы из браузера

Клиент обращается только к нашему `/api/products`. Сервер ищет по PostgreSQL и возвращает максимум 30 нужных продуктов. Полная база не скачивается на телефон, ключ USDA не попадает в браузер, а поиск не зависит от лимита внешнего API при каждом нажатии.

Основной путь — CSV-импорт, а не массовое скачивание через REST. Документация USDA описывает REST `/foods/search` и `/food/{fdcId}`, а также отдельные файлы для скачивания. Для публичного API USDA указан лимит 1000 запросов в час на IP; локальный импорт этот лимит не расходует.

- [Страница FoodData Central](https://fdc.nal.usda.gov/)
- [Скачивание наборов данных](https://fdc.nal.usda.gov/download-datasets/)
- [Руководство по API](https://fdc.nal.usda.gov/api-guide/)
- [Условия использования данных USDA](https://fdc.nal.usda.gov/data-documentation.html)

### Импорт

1. Скачайте нужный CSV-набор FoodData Central. Для обычных продуктов нужны Foundation/SR Legacy; для упакованных товаров и штрихкодов — Branded Food. Полный набор больше, но содержит всё перечисленное.
2. Распакуйте архив. В каталоге должны быть `food.csv`, `nutrient.csv`, `food_nutrient.csv`; `branded_food.csv` обрабатывается, если присутствует.
3. Укажите путь в `.env`:

```dotenv
USDA_CSV_DIR=C:/data/usda
```

4. Запустите при работающей PostgreSQL:

```bash
npm run import:usda
```

Импорт идёт потоково, не загружая весь CSV в память. Он нормализует единицы, обновляет существующие записи, подставляет названия категорий и пропускает отрицательные значения с записью их количества в журнал. На большом наборе первая загрузка может занять часы и потребовать заметного места на диске. Для регулярных обновлений используйте отдельный staging-импорт и переключение версии каталога только после успешной проверки; текущий скрипт — простой односерверный вариант.

`USDA_API_KEY` для CSV не нужен. При импорте каждый продукт автоматически получает русское отображаемое название и объединённый русско-английский `search_text`. Правила находятся в `server/localization.ts`: там словари продуктов, частей туши, способов приготовления и категорий, очистка лабораторных кодов USDA, а также подбор эмодзи. Это автоматическая правиловая локализация, а не ручная редактура всех 95 тысяч записей: названия брендов и часть редких кулинарных терминов могут оставаться латиницей, поэтому популярные карточки стоит постепенно проверять вручную.

Поиск использует PostgreSQL full-text search с русской морфологией и `pg_trgm`/`word_similarity` для опечаток. Учитываются разные формы и порядок слов, например «жаренная свинина», «свинина жареная» и «жареная свинино». Более затратный поиск с учётом опечаток запускается только при недостатке быстрых результатов. Ранжирование учитывает релевантность и полноту нутриентного профиля.

Массово обновить названия и поисковый текст после изменения правил локализации:

```bash
npm run localize:products
```

На VPS аналогичная команда выполняется в контейнере: `docker compose exec -T app npm run localize:products`. Скрипт пакетно обновляет записи через `server/localize-products.ts`; новые импортируемые продукты обрабатываются сразу, отдельный запуск после каждого импорта не требуется.

Каталог API поддерживает `GET /api/products?q=...&page=1&category=...` и возвращает `products`, `total`, `page`, `pageSize`, `totalPages`. Размер страницы — 30 продуктов. Список категорий с количеством записей доступен через `GET /api/product-categories`.

### Очистка каталога

Перед очисткой обязательно создайте резервную копию. Сценарий сначала удаляет продукты, у которых калории, белки, жиры и углеводы одновременно нулевые или отсутствуют. Вода, лёд, соль, уксус, кофе, чай и категория Spices and Herbs сохраняются как очевидные исключения.

Затем объединяются записи с одинаковыми русскими названиями без учёта регистра, повторных пробелов и `ё`/`е`. Остаётся вариант с наибольшим числом заполненных полей КБЖУ, затем — с наиболее полным нутриентным профилем. Ссылки дневника переносятся на оставленный продукт, избранное объединяется без повторов. Для удалённых нулевых продуктов ссылка дневника становится `NULL`, а сохранённый снимок продукта остаётся доступным.

Безопасный предпросмотр без изменений:

```bash
npm run cleanup:products
```

Применение на VPS после резервного копирования:

```bash
cd /opt/norma
./scripts/backup.sh
docker compose exec -T app npm run cleanup:products -- --apply
```

Очистка выполняется одной транзакцией. Повторный USDA-импорт может снова добавить удалённые исходные записи, поэтому после него нужно повторить локализацию, предпросмотр и очистку.

### Загруженные на VPS наборы

На тестовый сервер загружены и импортированы:

- **Foundation, April 2026** (`Foundation-2026-04-30`), каталог `/opt/norma/data/usda/foundation`;
- **SR Legacy, April 2018** (`SR-Legacy-2018-04`), каталог `/opt/norma/data/usda/sr-legacy`; это финальный выпуск SR Legacy, обновляться он не будет.

Исходные CSV не попадают в Git или Docker-образ. Compose монтирует `/opt/norma/data/usda` в контейнер как `/data/usda` только для чтения. Непосредственно после импорта и локализации в `products` было **95 803 записи**, включая служебный демо-каталог.

27 октября 2026 года очистка удалила **77 388 записей с нулевым КБЖУ** и объединила **9 027 повторов**. В рабочем каталоге осталось **9 388 продуктов**. Контрольные запросы подтвердили: нулевых кандидатов вне исключений — 0, групп повторяющихся нормализованных названий — 0, битых ссылок дневника — 0.

Повторный импорт на VPS:

```bash
cd /opt/norma

docker compose exec -T \
  -e USDA_CSV_DIR=/data/usda/sr-legacy \
  -e USDA_RELEASE=SR-Legacy-2018-04 \
  app npm run import:usda

docker compose exec -T \
  -e USDA_CSV_DIR=/data/usda/foundation \
  -e USDA_RELEASE=Foundation-2026-04-30 \
  app npm run import:usda
```

Повторный запуск обновляет записи по `fdc_id`, а не создаёт вторую копию продуктов. Статус последних запусков можно проверить в таблице `sync_runs`.

### Единицы и полнота

Все значения хранятся на 100 г в канонических единицах: ккал, г, мг или мкг. Список и соответствие полям USDA находятся в `src/nutrients.ts`. Интерфейс поддерживает до 92 показателей, но ни один источник не гарантирует их наличие у каждого продукта. Отсутствующее значение отображается как `—`, а не как ноль. Процент ДН показывается только для нутриентов с рассчитанной нормой.

USDA использует открытые данные, но перед публичным запуском сохраните атрибуцию и проверьте актуальные условия источника.

## Штрихкоды и Open Food Facts

Сначала сервер ищет штрихкод в PostgreSQL, затем запрашивает Open Food Facts API v2 и кэширует найденный продукт. Скачивать всю многомиллионную базу Open Food Facts на старте не требуется.

Нужно задать идентифицирующий `User-Agent`:

```dotenv
OFF_USER_AGENT=NormaNutrition/1.0 (your-email@example.ru)
```

Open Food Facts — краудсорсинговая база: продукта может не быть, состав может быть неполным или устаревшим. Пользователь должен сверить граммы и этикетку. Данные Open Food Facts распространяются по ODbL, изображения могут иметь отдельные условия; при публичном использовании нужны атрибуция и проверка лицензионных обязательств.

- [Open Food Facts API](https://openfoodfacts.github.io/openfoodfacts-server/api/)
- [Лицензии Open Food Facts](https://world.openfoodfacts.org/data)

Камера требует HTTPS, кроме локальной разработки на `localhost`. Если разрешение не дано, остаётся ручной ввод.

## Персональные нормы

### Калории

Для взрослых используется стартовая оценка основного обмена Миффлина–Сан Жеора:

```text
Мужчины: BMR = 10 × вес + 6,25 × рост − 5 × возраст + 5
Женщины: BMR = 10 × вес + 6,25 × рост − 5 × возраст − 161
```

Вес указывается в кг, рост в см. BMR умножается на коэффициент активности `1,2 / 1,375 / 1,55 / 1,725 / 1,9`. Для снижения веса применяется дефицит 15%, для набора — профицит 10%.

Это не универсально «лучшая» формула: ошибка у конкретного человека зависит от состава тела, уровня подготовки и фактической активности. Поэтому следующий правильный шаг — адаптация калорий по динамике веса и дневника за 2–4 недели, а не бесконечный выбор между формулами.

Исследования, использованные при выборе подхода:

- [Prado-Nóvoa и др., 2024 — проверка формул у людей с разной активностью](https://doi.org/10.1002/ajhb.24005)
- [Balci и др., 2021 — ограничения предсказательных формул у спортсменов](https://doi.org/10.3389/fphys.2021.625370)
- [Haroun и др., 2025 — сравнение формул в конкретной выборке](https://doi.org/10.1186/s13690-025-01727-9)

### Белок, жиры и углеводы

- Белок: от 1,0 г/кг при сидячем образе жизни до 1,6 г/кг в зависимости от активности и цели.
- Жиры: 30% калорий; насыщенные жиры ограничены ориентиром 10% калорий.
- Углеводы: оставшаяся калорийность после белка и жиров.

Метаанализ 74 РКИ показал небольшой дополнительный эффект потребления белка примерно от 1,6 г/кг/день на прирост мышечной массы у молодых людей при силовых тренировках. Это не означает, что каждому нужна именно такая норма: [Nunes и др., 2022](https://pubmed.ncbi.nlm.nih.gov/35187864/).

Микронутриентные ориентиры заданы в `calculateGoals()` и зависят от пола и возраста там, где это предусмотрено. Для развития этой части используйте актуальные справочники [NIH Office of Dietary Supplements](https://ods.od.nih.gov/factsheets/list-all/) и National Academies DRI.

Расчёт предназначен только для здоровых совершеннолетних и не является медицинской рекомендацией. Беременность, заболевания, лекарства, расстройства пищевого поведения и спортивная подготовка высокого уровня требуют отдельной модели или специалиста.

## Фото и помощник

Серверная интеграция использует Moonshot API:

```dotenv
MOONSHOT_API_KEY=секретный_ключ
MOONSHOT_BASE_URL=https://api.moonshot.ai/v1
MOONSHOT_VISION_MODEL=kimi-k3
MOONSHOT_TEXT_MODEL=kimi-k2.6
```

Документация: [Moonshot AI Platform](https://platform.moonshot.ai/docs) и [Kimi K3 Quickstart](https://platform.moonshot.ai/docs/guide/kimi-k3-quickstart). Для `kimi-k2.6` текстовый запрос отправляется с `thinking: { type: 'disabled' }` и `max_tokens`; для `kimi-k3` используются `reasoning_effort: low` и `max_completion_tokens`.

K2.6 выбран для пробного экономичного текстового режима. Moonshot объявил план вывода K2-моделей до конца декабря 2026 года: перед этим сроком нужно проверить доступность модели и при необходимости вернуть `MOONSHOT_TEXT_MODEL=kimi-k3`.

### Подключение на VPS

1. Зарегистрируйтесь в [Kimi API Platform](https://platform.moonshot.ai/), пополните баланс минимум на **$1** и создайте API Key.
2. На сервере выполните `nano /opt/norma/.env` и добавьте четыре переменные из блока выше, подставив настоящий ключ.
3. Сохраните файл и пересоздайте только приложение:

```bash
cd /opt/norma
docker compose up -d --force-recreate app
```

4. Откройте сайт, отправьте реальную фотографию и проверьте ответ помощника. Без ключа или при сбое API интерфейс показывает ошибку и кнопку повтора, не подставляя вымышленный продукт или рекомендацию.

Перед отправкой браузер уменьшает снимок до **1280 px по длинной стороне** с сохранением пропорций и кодирует его в JPEG с качеством **0,82**. Это сокращает объём загрузки; итоговая стоимость всё равно зависит от изображения и ответа модели. Процент `confidence` — самооценка модели, а не измеренная точность распознавания.

API возвращает до 12 отдельных позиций `items` с названием, примерной массой и уверенностью. Для каждой позиции сервер ищет продукт в каталоге. Если часть названий не найдена, они перечисляются в `unrecognized`, а остальные продукты всё равно доступны для добавления. В интерфейсе у каждой позиции есть своя масса и кнопка «+»; добавленная позиция удаляется из предложенного списка. Кнопка «Добавить все» переносит оставшиеся позиции в выбранные дату и приём пищи.

Ключ задаётся только в серверном `.env` с правами `600`. Нельзя переносить его в `VITE_*`, React-код, мобильное приложение, Git, командную строку или чат. Фото отправляется на наш backend, а уже backend обращается к модели.

### За что платит приложение

Модель определяет названия продуктов и примерные массы, но **не выдумывает КБЖУ по пикселям**. Численный состав берётся из каталога, а продукты и порции подтверждает пользователь. Текстовый помощник получает текущий дневник, нормы и задачи, поэтому может учитывать питание при обсуждении тренировки.

На 28 октября 2026 года для `kimi-k3` указаны **$3 за 1 млн входных и $15 за 1 млн выходных токенов**, кэшированный вход — **$0,30 за 1 млн**, запись контекстного кэша на 5 минут — **$3 за 1 млн**. Для `kimi-k2.6` указаны **$0,95 за 1 млн входных, $4 за 1 млн выходных и $0,16 за 1 млн кэшированных входных токенов**. Условный пример K3 без кэша: 2 000 входных и 300 выходных токенов стоят `$0,006 + $0,0045 = $0,0105`; 1 000 таких запросов — примерно **$10,50**. Это не фиксированная цена фотографии: изображение занимает зависящее от него число токенов, а рассуждения модели также входят в выходной расход. Актуальные условия: [Model Pricing](https://platform.moonshot.ai/docs/pricing/chat).

### Фактическая себестоимость запросов

Каждый успешный ответ Moonshot API сохраняется в таблице `ai_usage` с типом `photo` или `chat`, моделью, всеми категориями токенов и рассчитанной стоимостью в USD. Обычный вход, попадание в кэш и запись кэша не складываются дважды: их доли вычитаются из общего `prompt_tokens`. Стоимость фиксируется на момент запроса и не пересчитывается задним числом. Для неизвестной модели токены сохраняются, а стоимость остаётся `NULL`, чтобы не выдавать неточный расчёт.

Авторизованный пользователь может открыть `/api/ai-usage`: endpoint возвращает последние 100 собственных запросов и сводку по количеству, токенам, общей и средней себестоимости отдельно для фото и текста. Доступ к чужой статистике отсутствует. Учитываются только запросы после установки этой версии; стоимость инфраструктуры и налоги в расчёт не входят. Ошибка записи статистики не прерывает основной ответ пользователю.

Для административной сводки на VPS:

```bash
cd /opt/norma
docker compose exec db psql -U norma -d norma -c "SELECT kind, count(*) AS requests, sum(total_tokens) AS tokens, round(sum(total_cost_usd), 6) AS cost_usd, round(avg(total_cost_usd), 6) AS average_usd FROM ai_usage GROUP BY kind ORDER BY kind;"
```

## Настоящий SMS-вход в России

Обычно подключают SMS-агрегатора или операторский API: заключают договор, выбирают тариф, регистрируют имя отправителя, если оно требуется, получают API-ключ и вызывают HTTPS API провайдера. Условия зависят от провайдера и юридического статуса владельца сервиса.

Сейчас в `server/auth.ts` реализован универсальный контракт:

```http
POST SMS_PROVIDER_URL
Authorization: Bearer SMS_PROVIDER_TOKEN
Content-Type: application/json

{"phone":"+79175133315","text":"Ваш код ..."}
```

Это **не готовая интеграция со всеми провайдерами**. Для выбранного SMSC, SMS Aero, операторского или другого API нужен небольшой адаптер под его параметры и подпись запроса.

В production:

1. удалите `DEV_SMS_CODE` или оставьте его пустым;
2. задайте `SMS_PROVIDER_URL` и `SMS_PROVIDER_TOKEN`;
3. добавьте ограничение запросов по IP, а не только по номеру, защиту от перебора и SMS-фрода;
4. не записывайте коды в логи;
5. храните минимум данных, опубликуйте политику и получите необходимые согласия;
6. отдельно проверьте требования 152-ФЗ и правил провайдера с юристом — этот README не заменяет юридическую оценку.

Код живёт 5 минут, допускается 5 попыток, в базе хранится HMAC кода, а не сам код.

## Как запоминается вход

Выбрана серверная opaque-сессия, а не JWT:

- случайный 256-битный токен находится в cookie `HttpOnly; Secure; SameSite=Lax`;
- JavaScript не читает этот токен, и он не лежит в `localStorage`;
- PostgreSQL хранит только SHA-256-хеш токена;
- срок сессии — 30 дней, токен ротируется каждые 7 дней;
- выход удаляет серверную сессию;
- разные устройства получают независимые сессии.

Для одного backend это проще отзывать и контролировать, чем самодостаточный JWT. `Secure` включается при `NODE_ENV=production`, поэтому публичный вход требует HTTPS. Если появятся cross-origin запросы или отдельный домен API, понадобятся продуманные CORS и CSRF-защита; просто ослаблять `SameSite` не следует.

## Публикация в интернет

### Вариант 1: домашний компьютер + Cloudflare Tunnel

Это самый простой вариант без статического IP и проброса портов. Компьютер должен оставаться включённым, а tunnel — работать как служба.

1. Запустите production-приложение и PostgreSQL через `docker compose up -d --build`.
2. Настройте настоящий SMS и уберите демо-код.
3. Установите `cloudflared` и создайте именованный tunnel по [документации Cloudflare](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/).
4. Направьте ingress на `http://127.0.0.1:3001` и привяжите поддомен, например `food.example.ru`.
5. Проверьте HTTPS, повторный вход после перезапуска браузера, камеру и резервную копию.

Для временной проверки существует `cloudflared tunnel --url http://127.0.0.1:3001`, но случайный публичный адрес не стоит использовать как постоянный production-адрес.

### Вариант 2: VPS + домен + Caddy

1. Возьмите VPS с Docker и создайте DNS `A`-запись на его IP. Запись `AAAA` добавляйте только при настроенном IPv6.
2. Откройте только порты 22, 80 и 443; PostgreSQL и Node.js наружу не публикуйте.
3. В `.env` задайте `DOMAIN=food.example.ru`, новые секреты и настройте SMS.
4. Запустите `docker compose --profile public up -d --build`.

Caddy автоматически получает и обновляет HTTPS-сертификат. Проверка: `https://food.example.ru/api/health`.

Проброс портов на домашнем роутере тоже возможен, но часто мешает CGNAT, динамический IP и риск открыть лишний сервис. Для домашнего варианта предпочтителен tunnel.

## Резервные копии и эксплуатация

На VPS резервная копия PostgreSQL создаётся ежедневно в **03:17 UTC (06:17 по Москве)**. Файлы хранятся в `/opt/norma/backups`, срок хранения — 14 дней. Расписание находится в `/etc/cron.d/norma-backup`.

Ручное создание копии:

```bash
cd /opt/norma
./scripts/backup.sh
```

Скрипт использует `pg_dump -Fc`, проверяет, что файл не пустой, и удаляет копии старше 14 дней. Перед восстановлением проверяйте копию через `pg_restore --list` и сначала разворачивайте её в отдельной пустой базе. Локальная копия на том же диске не заменяет внешнее зашифрованное хранилище — его нужно подключить отдельно.

Перед реальными пользователями также нужны внешний мониторинг `/api/health`, алерты, централизованные логи без кодов и токенов, ограничение частоты запросов по IP и регулярное копирование резервных файлов в другое хранилище.

## Синхронизация и текущие ограничения

`PUT /api/state` сейчас использует стратегию **last write wins**: последнее сохранённое состояние заменяет дневник, задачи, избранное и сообщения пользователя. Для одного активного устройства это просто, но при одновременном редактировании на двух устройствах возможна потеря изменений. Следующая серверная итерация — отдельные операции создания/изменения, `updated_at`, версии записей и очередь офлайн-синхронизации.

Другие ограничения:

- полный перевод всех названий USDA ещё не сделан;
- пользовательские продукты и ручное редактирование состава пока не реализованы;
- состав смешанного блюда по фото не разбивается на ингредиенты;
- уведомления и нативные мобильные сборки не реализованы;
- нормы не адаптируются автоматически по динамике веса;
- повторяющиеся задачи хранят правила повторения, но не создают отдельные экземпляры на будущие даты;
- универсальный SMS-контракт требует адаптера выбранного провайдера.
